이전 글에서는 MSVC와 gcc의 unordered_map 구현체를 분석했는데 다른 구현 방식도 궁금해서 찾아보다가 예전에 잠깐 봤던 folly 라이브러리에서는 unordered_map을 F14Map이라는 이름의 자료구조로 구현해 놨더라고.
구현체마다 컨셉이 확실해서 코드 분석이 참 즐거웠어. 그럼 시작할게.


- 개요
folly는 meta에서 내부적으로 만들어서 사용하는 stl인데 gcc나 MSVC 코드보다가 이거 보니까 최신 코드라 그런지 인덴트도 정배열이고 변수명도 명확해서 편하게 읽을 수 있었어. (gcc는 변수에 언더바가 너무 많아..)

folly에서는 F14Map이라는 자료구조를 만들어서 사용하는데 F14 이름의 뜻은 14방향 필터를 사용하는 해시 테이블을 말해.
이게 무슨 소리냐면 해시 테이블에서 bucket 하나에 최대 14개까지 저장하고, 이걸 SIMD 128bit 연산 한번으로 14개를 필터링 하는 방식이라는 거야.
컨셉 자체만 보면 참신한데 조금만 생각해봐도 꼬리물기 질문이 나올 수밖에 없는 설계야. 그런 여러가지 상황들을 어떻게 극복했는지 순차적으로 알아볼게.
(참고로 코드에서는 bucket 대신 chunk로 사용하는데 편의상 bucket으로 칭할게.)


- 14개 해시값의 일괄 비교
보통 해시값을 32bit 정수로 저장하는데 SIMD 128bit로 비교하면 한번에 4개까지만 비교가 가능하잖아? 이걸 14개까지 늘려서 비교할 수 있는 이유는 bucket에서 비교하는 키는 해시값 전체가 아닌 상위8bit만 잘라서 비교하기 때문이야.
여기서는 이 값을 tag라고 부르고 있는데, 만약 해시값이 0xABCDEF12 인 노드가 있을 때 tag는 0xAB인거지.

다만 이렇게 하면 해시값이 다른데도 동일한 tag가 하나의 bucket에 여러 개 존재하는 경우가 있을거잖아?
그래서 검색할 때 14개 tag를 SIMD에 전달하고 tag가 일치하는 인덱스의 비트를 1로 기록해서 2진수 14bit로 00100110 이런 식으로 받아서 1이 기록된 인덱스 비트를 for문으로 돌면서 그때서야 해당 인덱스의 노드가 지금 검색한 해시값과 동일한 지 비교하게 돼.
14개 중에 동일 tag가 존재할 가능성이 많지 않기 때문에 기껏해야 2,3번 더 비교하는 정도일거야.

이 방식의 장점은 chaining된 멤버를 순회하며 하나씩 비교하지 않고, SIMD로 14개 tag를 동시에 비교해서 높은 적중도로 대부분 한번에 찾아낼 수 있어. (해시값 분포도가 적당히 균일하다는 가정 하에 말이야)
F14.md 파일에 자세한 설계 내용이 있는데, 여기 적힌 테스트 결과를 보면 존재하는 키를 검색할 때 평균 탐색 길이가 1.04라는 실제 수치도 제시해놨어. 키를 100번 검색하면 대부분 한번에 찾았고 4번만 두번 검색했다는 뜻이야. 엄청난 적중률이지.

여기서 하나 더 궁금할거야. SIMD 128bit 연산인데 왜 16개를 비교하지 않고 14개만 비교할까?
왜냐하면 나머지 16bit에는 bucket의 메타 데이터 두 개가 기록되어 있거든. 그건 현재 bucket에 저장된 다른 bucket 데이터 개수와 이 bucket에서 overflow된 멤버 개수에 각각 1byte를 할애해서 저장하고 있어.
(다만 이 동작까지 자세히 설명하려면 지나치게 복잡해지니까 여기선 생략할게.)

여기서 하나의 bucket에 최대 14개까지 chaning이 가능하다고 했는데 그럼 14개가 넘어가면 어떻게 해야할까?
정답은 14개까지만 기록하고, 그 이후에 tag에 특정 가중치를 계산해서 다음 bucket을 찾고, 거기에 추가하는 방식을 사용하고 있어.
여기가 이번 글에서 가장 복잡한 부분이니 세부적인 예시를 들어볼게.

2번 bucket에 해시값 0x78123456(tag는 0x78이겠지)을 추가했는데 2번 bucket은 이미 14개가 다 차있어서 다음 bucket에 넣어야 하는 상황이야.
이 때, 2번 다음 bucket을 계산하는 건 bucket마다 정해져있는게 아니라 찾는 해시값의 tag를 통해 (현재 bucket + tag값 * 2 + 1) / bucket_count 로 다음 bucket이 결정되는거야.

위 예제로 해시값 0x78123456이 다른 bucket에 입력되었을 때 그 해시값을 탐색하는 경로를 자세히 알아보면,
일단 주어진 해시값으로 2번 bucket임을 알아내고, 2번 bucket에서 14개 키를 tag 0x78값으로 비교했는데 여기에는 없을거잖아? (혹은 tag는 같더라도 해시값이 다르겠지) 
그래서 다음 탐색할 bucket을 (현재 bucket+tag*2+1) / bucket_count로 tag기준으로 bucket 번호를 알아내서 (여기선 5번이라고 할게) 5번 bucket에 tag값을 비교해서 찾아낼 수 있을거야.
여기선 tag값이 0x78일 때 검색할 다음 bucket이 5번이었지만, tag값에 따라 다음 bucket이 달라지겠지.


- SIMD 연산 구현의 상세 분석
이와 관련한 구현부를 조금 분석해보면, SSE2 명령어인 _mm_set1_epi8, _mm_cmpeq_epi8, _mm_movemask_epi8 를 사용하고 있어.
_mm_set1_epi8 함수는 전달받은 8bit 값을 16번 반복해서 128bit에 채워넣는 기능이야. 함수에 0x78을 넣으면 0x78787878.. 이렇게 된 변수를 반환해.
그리고 _mm_cmpeq_epi8 함수는 두 개의 128bit를 받아서 8bit단위로 각각 값이 같은지 비교하는데 두 값이 같으면 0xFF, 다르면 0x00을 기록해서 반환하게 돼. 
예를 들어 A는 검색할 tag가 반복된 128bit, 그리고 B는 해당 bucket의 tag값(8bit) 14개를 넣고 아래처럼 함수에 A,B를 넣으면 각 바이트마다 비교한 R값이 나오게 돼. 여기선 편의상 32bit만 쓸게.

A: 0x78787878
B: 0x78123478
---------------
R: 0xFF0000FF

여기 나온 R값을 _mm_movemask_epi8 함수에 넣으면 각 바이트의 최상위 비트를 모아서 16bit 정수 마스크를 생성하게 돼.

int mask = _mm_movemask_epi8(R);
// mask: 0x09 (이진수: 1001)

이렇게 나온 mask를 가장 낮은 자리에 1이 설정된 비트 인덱스를 반환하는 _BitScanForward 인트린식 함수를 사용해서 인덱스를 얻어오는 식으로 반복문을 사용해서 최종적으로 tag가 동일한 해시값 인덱스를 가져올 수 있어.
저 예시를 기준으로 본다면 반복문으로 tag 0,3 인덱스를 확인하는 로직을 실행하게 될거야.

혹시 SSE2(Streaming SIMD Extensions) 명령셋의 호환성이 문제되진 않을까 해서 찾아보니 2000년 중반 이후의 x86/64 cpu는 모두 지원하는 명령셋이라 범용적으로 쓰기에 무리는 없었어. 
다만 x86/64 아키텍처가 아닌 ARM/Apple silicon(m1,m2..)에 대해서 전처리기 분기문을 통해 해당 아키텍처에 맞는 벡터 함수(vdupq_n_u8 등)로 분기해놨고, 아예 사용이 안되는 케이스(임베디드라던가)에서도 문제가 없도록 unordered_map을 동일 인터페이스로 맵핑한 F14MapFallback 클래스를 제공해서 호환성을 고려한 꼼꼼함도 눈여겨볼 만해.


- F14Map의 여러가지 상속 구현체 소개
사실 F14Map에는 해시맵에 대한 탐색 알고리즘이 공통으로 구현되어 있을 뿐이고, 실제로 이걸 상속받아 사용하는 최종 구현체는 F14NodeMap, F14ValueMap, F14VectorMap 세 가지 자료구조야.
각 클래스는 값의 데이터 저장 방식에 따라 다르게 구현하여 상황에 맞게 효율적으로 사용할 수 있어. 

F14NodeMap은 기존 unordered_map처럼 실제 값이 할당된 포인터를 슬롯이 소유하는 방식이야.
F14ValueMap은 값을 슬롯에 키와 같이 저장해서 메모리 효율을 올리는 구조야. 다만 값을 그대로 저장하니까 값의 크기가 커질수록 여러가지로 비효율이 되는데, 간단한 필드 두세개를 저장할 때는 이보다 좋을 수 없겠지.
F14VectorMap은 값을 하나의 연속된 배열에 저장하고, 해시키에는 이 배열의 인덱스를 저장하는 방식으로 구현해서 중간 크기의 값에 효율적인 방식을 택했어.

모든 자료구조는 상황에 맞게 써야하는데 이것 역시 세 가지 중에서 저장할 자료의 특징을 제대로 알아야 효율적으로 쓸 수 있어.
NodeMap으로는 중/대형(혹은 비정형/추상 클래스) 데이터에 사용하는게 좋고, ValueMap은 값의 크기가 작고 빈번할 때 사용하고, VectorMap은 중간 크기 정도에 사용하는게 좋아.
그런데 모든 사람이 이런 구현체의 세부 방식을 하나씩 알 수는 없잖아? 그래서 값 크기에 따른 자료구조 선택의 모호함을 줄이기 위해서 F14FastMap이라는 구현체를 만들어놨는데, 값의 크기가 24byte 미만이면 ValueMap, 그 이상이면 VectorMap을 상속받아 사용해서 이 모호함을 극복했어.
(아마 meta 내부 룰에서는 F14FastMap 사용을 권장하도록 되어있겠지.)

여기의 ValueMap과 비슷한 저장 구조를 redis의 ziplist라는 자료구조가 사용하는데, 거기에서는 특정 개수 혹은 특정 크기 이하의 데이터일 때에는 ziplist를 사용하다가 그걸 넘어가면 동적으로 다른 자료구조로 변환하는 방식으로 사용하고 있어.
예를 들어 sortedset은 멤버가 128개가 넘어가는 즉시 ziplist에서 skiplist로 자료구조가 바뀌게 돼. 이런 설정값은 서비스의 특성에 맞는 값을 설정하는게 좋겠지.
https://redisgate.kr/redis/configuration/internal_ziplist.php


- 그 외 folly 분석하면서 재밌던 점
최근 문법들이 여기저기 있는게 인상적이었어. 예를 들면 반복문 곳곳에 c++20에 추가된 [[likely]]가 자주 보였거든.
이 지시어는 컴파일러가 명령어 배치를 할 때에 해당 분기가 실행될 확률이 높다라는걸 표시하는 힌트인데 이렇게 컴파일하면 명령어를 연속적으로 배치해서 cpu 파이프라인이 연속되도록 보조해 주는 기능이야.
거의 실행되지 않을 예외처리나 가드 코드에는 반대로 [[unlikely]]를 달아놓으면 해당 로직을 주요 로직에서 멀리 떨어진 메모리 영역에 배치해서 조금이나마 효율을 높일 수 있기도 해.

gcc에서는 3.0부터 이미 __builtin_expect라는 내부 함수로 컴파일러에게 알려주고 있었는데 MSVC 컴파일러에는 저 함수가 없어서 gcc일때만 동작하게 전처리기로 묶어두는게 일반적이었어.
이게 c++20에 들어갔다는 건 대충 알았는데 이렇게 적극적으로 쓰고 있는걸 보니까 참 꾸준히 관리되고 있구나 싶었어.

그리고 최근 커밋들도 잠깐 구경해봤는데 꽤 재밌는 최적화 아이디어들이 적용되었더라고.
코드도 재밌었는데 커밋 설명에 이 수정의 케이스별 성능 개선 수치와 의도 외에 실제 자원 절약 예상치(cpu, kW, 금액 등)도 자세히 써놓은게 뭔가 특이했어.
보통 최적화 벤치마크에 대한 문서는 이로 인해 성능이 얼마나 더 좋아지는지만 써놓잖아? 근데 소요되는 kW에 더불어 연간 절약되는 금액을 보니까 정량적인 성과 측정이 이뤄지는 편인가 싶기도 하고..

- Bloomberg STL
여기도 자체 자료구조를 쓰고 있어서 unordered_map을 잠깐 확인해보니 gcc랑 구조가 거의 비슷했어.
bucket 크기를 소수 테이블에서 선정하는거나 데이터 저장 구조같은거 말이야.
그래서 따로 글로 옮기진 않았는데, 재밌었던 부분은 헤더 파일에 해당 자료구조의 메모리 할당, 설정 방법, 특이 사항, 사용 방법 등이 주석 1000줄을 할애해서 적혀있다는 거였어.
특히 외부 노출되는 모든 함수에 대한 big-O표(아래 테이블)가 포함되어 있는건 참신했어.
unordered_map 외에 다른 자료구조 헤더 파일에도 다 비슷한 형식으로 써있던거 보고 그 많은 분량에 한번 더 놀라게 되더라.

+--------------+---------------+
| Operation    | Complexity    |
+==============+===============+
| a.clear()    | O[n]          |
+--------------+---------------+
| a.find(k)    | Avg  : O[1]   |
|              | Worst: O[n]   |
+--------------+---------------+
| a.rehash(k)  | Avg  : O[n]   |
|              | Worst: O[n^2] |
+--------------+---------------+


- 결론
1) folly의 F14Map 자료구조는 SIMD 연산을 이용하여 최대 14개의 해시를 대략적으로 한번에 비교하는 방식으로 탐색을 최적화했다.
2) 최종 구현체에는 저장 공간 최적화를 여러 방식으로 구현해놔서 상황에 맞게 선택하여 효율적으로 사용할 수 있다.
3) meta나 bloomberg stl을 가져와서 자신의 서비스에 포함시킨 회사도 있으려나.
4) 며칠 전까지도 최적화 코드가 들어갔던데 이건 AI가 최적화할 부분을 알려준걸까 아닐까.. (그냥 뻘생각)
